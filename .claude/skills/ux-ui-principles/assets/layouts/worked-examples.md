# ตัวอย่างการใช้ layout กับโจทย์จริง

ตัวอย่างสมมติที่เขียนขึ้นสำหรับ skill นี้ ยังไม่ได้ทดลองกับผู้ใช้หรือระบบจริง
ชื่อ ราคา ข้อมูล และ business rules เป็นข้อมูลตัวอย่าง ต้องแทนด้วยข้อมูลโครงการ
ใช้ [shared specification](specification.md) เป็นขอบเขตการส่งมอบ

## ตัวอย่าง 1: Checkout ซื้อสินค้าบนมือถือ — C04

**โจทย์:** ผู้ใช้ซื้อสินค้าและตรวจยอดก่อนชำระเงิน มีที่อยู่จัดส่งและ payment provider
**สมมติฐาน:** ผู้ใช้ซื้อแบบ guest ได้ ค่าส่งคำนวณหลังระบุที่อยู่ ระบบเก็บค่าฟอร์มทั่วไปได้
**เหตุผล:** ใช้ form + order summary เพื่อให้กรอกข้อมูลพร้อมตรวจสิ่งที่กำลังซื้อ
การแบ่งเป็นหลายขั้นทำได้หากข้อมูลมีมาก แต่ต้องรักษาค่าและย้อนกลับได้

Wide:

```text
┌──────────────────────────────┬───────────────────────┐
│ Checkout / กลับไปตะกร้า      │ สรุปคำสั่งซื้อ          │
│ 1. ติดต่อ                   │ สินค้า × จำนวน          │
│ อีเมล / เบอร์โทร             │ ราคาสินค้า / ค่าส่ง     │
│ 2. ที่อยู่จัดส่ง              │ ยอดรวมหลังคำนวณ         │
│ ชื่อ / ที่อยู่ / รหัสไปรษณีย์ │ เงื่อนไขที่เกี่ยวข้อง    │
│ 3. วิธีชำระเงิน              │                       │
│ Error summary เมื่อส่งผิด    │                       │
│ [ชำระเงินตามยอดที่ยืนยัน]     │                       │
└──────────────────────────────┴───────────────────────┘
```

Compact: สรุปสินค้าและยอด → ติดต่อ → ที่อยู่ → วิธีชำระ → ยอดยืนยันและปุ่ม
รายละเอียดสินค้ายุบได้หากยังมีสรุปที่พอเข้าใจ ยอดก่อนคำนวณต้องระบุว่าเป็นประมาณการ
ไม่ทำ sticky ปุ่มจนบัง field หรือ error ขณะ keyboard เปิด

**เนื้อหา/controls:** ใช้ label เห็นตลอด ระบุ optional ให้ชัด ช่องชำระเงินใช้
integration ของ provider; เปลี่ยนที่อยู่แล้วแจ้งว่าค่าส่งอาจเปลี่ยนก่อนยืนยันยอด

| State | Behavior ที่เสนอ |
|---|---|
| Ready | แก้ข้อมูลและตรวจยอดที่ระบบยืนยันได้ |
| Validation | รักษาค่าที่อนุญาต แสดง error summary และ error ข้าง field |
| Submitting | แจ้งกำลังชำระ กันการส่งซ้ำ และใช้การป้องกันรายการซ้ำฝั่งระบบ |
| Unknown outcome | ตรวจสถานะรายการเดิมก่อนเสนอให้ชำระใหม่ |
| Failed confirmed | บอกวิธีกู้คืน เก็บข้อมูลที่อนุญาต และให้ลองใหม่อย่างปลอดภัย |
| Success | แสดงเลขรายการ ยอด และขั้นตอนถัดไปเมื่อผลยืนยันแล้ว |

**Keyboard/focus:** ลำดับตามฟอร์ม; failed validation ให้ focus summary ตาม
pattern ที่เลือกและเชื่อมไปช่องผิด; แยกการแจ้ง status ที่ไม่ต้องแย่ง focus

**Acceptance:** ส่งข้อมูลที่มีรหัสไปรษณีย์ผิดแล้วช่องอื่นยังอยู่ แก้และส่งใหม่ได้;
แตะชำระซ้ำบนเครือข่ายช้าไม่เกิดรายการซ้ำ; timeout แล้วระบบตรวจรายการเดิมได้
ต้องตรวจจริงทั้ง frontend และ provider/server ไม่สรุปจาก wireframe

## ตัวอย่าง 2: Admin จัดการคำขอ — A01 + A02

**โจทย์:** เจ้าหน้าที่ค้นคำขอ เปิดรายละเอียด และอัปเดตสถานะภายใต้สิทธิ์ของตน
**สมมติฐาน:** มี request ID, ผู้ขอ, วันที่, สถานะ และผู้รับผิดชอบ; ยกเลิกเป็นงานที่มีผลสำคัญ
**เหตุผล:** table ใช้ค้นและเทียบหลาย record; detail ใช้อ่านข้อมูล/ประวัติเต็ม
ใช้หน้า detail เมื่อเนื้อหายาวหรือจำเป็นต้อง deep link แทน panel ที่แคบเกินไป

```text
┌───────────────┬────────────────────────────────────────┐
│ Navigation    │ คำขอ | [สร้างคำขอ]                    │
│ • คำขอ       │ Search | สถานะ | เจ้าหน้าที่ | วันที่    │
│ • ทีม         │ Applied filters | ผลลัพธ์ที่พบ          │
│ • รายงาน      │ □ ID | ผู้ขอ | วันที่ | สถานะ | เจ้าของ  │
│               │ □ R-102 | ...                          │
│               │ จำนวนที่เลือก + ขอบเขต bulk action      │
│               │ Pagination                             │
└───────────────┴────────────────────────────────────────┘
```

Compact: หัวข้อ/search → filters ใน panel → active filters → รายการที่มี ID,
สถานะและเจ้าของ → detail; ถ้าต้องเทียบคอลัมน์จริงให้มี table region ที่เลื่อนได้
อย่าตัดข้อมูลที่จำเป็นต่อการตัดสินใจเพียงเพื่อให้ทุก record เป็น card

**Detail:** ID + status + permitted actions → ข้อมูลคำขอ → ประวัติ → related records
กลับ list แล้วรักษา query, filters และตำแหน่งตาม contract ที่กำหนด

**States:** initial empty แนะนำสร้าง/นำเข้า; filtered empty แนะนำแก้ filter;
permission denied อธิบายการขอสิทธิ์; concurrent edit แสดง conflict;
bulk partial failure แสดง record ที่สำเร็จ/ล้มเหลวและทางกู้คืน

**Selection:** ระบุชัดว่าเลือกเฉพาะหน้านี้หรือทุก record ที่ตรง filter
เปลี่ยน filter แล้วต้องกำหนดนโยบาย selection ที่แน่นอนและมองเห็นได้
ก่อนยกเลิกหลายรายการ แสดงรายการ/จำนวนและผลที่เกิดขึ้นตามความเสี่ยงของงาน

**Accessibility:** ใช้ table headers และชื่อ checkbox ที่ระบุ record;
ประกาศจำนวนที่เลือกอย่างเหมาะสม; เปิด drawer/modal ต้องมี keyboard/focus contract
สิทธิ์ฝั่ง UI ต้องสอดคล้องกับการบังคับใช้ฝั่งระบบ

**Acceptance:** ค้น R-102 เปิด detail แล้วกลับมายังผลเดิม; เลือกหลายรายการเห็น
scope ชัดเจน; เมื่อหนึ่งรายการเปลี่ยนไม่ได้ ระบบแสดงผลรายรายการและไม่อ้างว่าสำเร็จทั้งหมด

## ตัวอย่าง 3: จองบริการตามเวลา — C05

**โจทย์:** ผู้ใช้เลือกบริการ สาขา วันเวลา และรับรายละเอียดการนัดหมายที่ยืนยันแล้ว
**สมมติฐาน:** เวลามีจำนวนจำกัด มีผู้ใช้อื่นจองพร้อมกัน และแสดง timezone ของสาขา
**เหตุผล:** ให้เลือกบริการก่อนแสดงเวลาที่ใช้ได้ ช่วยไม่ให้เลือก slot ที่ใช้กับบริการนั้นไม่ได้
สามารถรวมวันและ slot ในหน้าเดียวเมื่อเลือกได้ง่าย ไม่ต้องใช้ calendar grid เสมอ

```text
┌────────────────────────────────┬─────────────────────┐
│ บริการ + สาขา                  │ สรุปการจอง          │
│ เลือกวัน | timezone ที่แสดงชัด  │ บริการ / สาขา       │
│ [09:00] [10:30] [13:00]        │ วัน เวลา ระยะเวลา    │
│ รายละเอียดผู้เข้ารับบริการ      │ ราคา/เงื่อนไข        │
│ ข้อผิดพลาดหรือ slot เปลี่ยน     │ สิ่งที่ต้องเตรียม    │
│ [ตรวจทานและยืนยัน]              │                     │
└────────────────────────────────┴─────────────────────┘
```

Compact: บริการ/สาขา → วัน/slot → ผู้เข้ารับบริการ → สรุปและยืนยัน
มีวิธีเลือกวันที่ใช้ keyboard ได้ และแสดงวัน/เวลาแบบข้อความอ่านง่าย
ถ้าใช้ hold ให้แสดงความหมายและหมดอายุจริง; ไม่สร้าง countdown หากระบบไม่มี hold

**States:** ไม่มี slot → เปลี่ยนวัน/สาขา; slot ถูกผู้อื่นจอง → แจ้งและคงข้อมูลอื่น;
hold expired → ให้เลือกใหม่; pending → กันการส่งซ้ำ; success → เลขนัดหมาย
วันเวลา timezone สถานที่ และวิธีเปลี่ยน/ยกเลิก

**Tradeoff:** calendar ช่วยเห็นภาพรวมวัน แต่ list ช่วยเลือกเวลาที่มีให้ได้โดยตรง
เลือกจากความหนาแน่นของเวลาและงานจริง ไม่บังคับทั้งสองแบบทุกโครงการ

**Acceptance:** ผู้ใช้บอกวันเวลาและสถานที่นัดได้ถูกต้อง; slot เปลี่ยนขณะยืนยันแล้ว
ระบบไม่สร้างการจองผิดเวลา; ผู้ใช้เลือกเวลาใหม่โดยไม่ต้องกรอกข้อมูลทั่วไปทั้งหมดอีกครั้ง

## วิธีนำตัวอย่างไปใช้

แทนข้อมูลสมมติด้วยข้อมูลจริง ระบุ assumption ที่ยังไม่ยืนยัน เชื่อมกับ tokens
ของโครงการ และเขียน acceptance ตามผลที่ผู้ใช้ต้องทำให้สำเร็จ รายงานให้ชัดว่าเป็น
specification, prototype หรือ implementation ที่ตรวจแล้ว ห้ามใช้คำว่า build เสร็จ
เมื่อมีเพียงข้อความหรือ wireframe
