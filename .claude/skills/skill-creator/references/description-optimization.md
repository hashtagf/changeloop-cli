# Description optimization

Use [skill-evaluation](../../skill-evaluation/SKILL.md) for observed trigger
comparisons. A description states the task, realistic triggers, exclusions,
and neighboring owner. Avoid broad keyword capture or instructions granting
permissions. A realistic user request should select one primary owner.

## Cases

Include substantive should-trigger, should-not-trigger, and ambiguous requests
at each changed boundary. Cover relevant languages and nearby competing skills.
Use actions and artifacts as expected outcomes rather than matching a slogan.
Read the proposed catalog cases as inputs, not results.

Present cases inline or in an optional local viewer when useful. Reuse settled
user intent; ask only for missing material choices. No export or empty feedback
constitutes approval. Read only the exact user-selected feedback file.

## Run and select

Pin current metadata and baseline, choose a real supported runner/model, and
confirm scope, budget, and any paid/external authority. Do not infer a runnable
model identifier from the assistant's display name. No runner means not-run.

If using bundled run_loop tooling, inspect its supported host and side effects
first. Run only against an isolated candidate copy within allowed paths; the
tool must not edit the installed catalog or approved agreement. Keep runs
attached/managed under current host policy and capacity. Its iteration cap is
an experiment budget, never a product-repair retry ceiling.

Separate tuning cases from held-out confirmation. Do not select a winner using
held-out results and then present those same results as independent confirmation.
Repeat matched cases enough to report uncertainty; record missed and false
triggers plus actual behavior. Unknown timing, usage, and costs stay unknown.

Apply the supported candidate to the active Build workspace, check the full
body and references for consistency, and resume the harness. If live experiments
were not run, report the revision as structurally checked, not empirically better.
